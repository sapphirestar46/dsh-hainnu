## 面板里的「可用模型」

面板新增一张「可用模型」卡片，数据来自宿主的 `/dsh-hainnu/status` → `models` 字段
（由 `lib/models.js` 生成，面板不硬编码）。每个模型展示：

- 来源标签（海师自部署 / 海师阿里云）、本地 id、上下文与输出上限；
- `summary` 一段话简介；
- 能力标签：**支持图片 / 纯文本**、**原生工具调用 / 模拟工具调用**；
- `notes` 逐条备注（能不能看图、工具稳不稳、建议怎么用）。

结论就是实测得到的那几条：只有自部署的 `deepseek-flash` 能看图、走原生 function calling；
三个平台模型是插件用文本协议模拟工具调用，`deepseek-v4.1-flash` 最快最稳，`kimi-k3` 偶有波动。

## 对话窗口里的「1017」角标

DSH 新版给官方 DeepSeek Flash 的模型标签挂了 `1017` 发行角标，实现是内置插件
`@deepseek-ai/dsh-client-ui-deepseek-model-label-1017` 往
**`conversation.input.model.label`** 槽位注册一个组件：

```js
function DeepSeekModelLabel({ provider, model, t }) {
  if (!(provider.id === 'deepseek-official' || provider.id === 'deepseek-account')
      || model.id !== 'deepseek-flash' || model.name !== 'DeepSeek-V4.1-Flash') return model.name;
  return <span>{model.name} <Tag tone="info">1017</Tag></span>;
}
```

它写死只认那两个 provider，我们的 provider 是 `hainnu`，所以拿不到。插件改成**往同一个槽位
注册自己的组件** `ComposerModelLabel`：`provider.id === 'hainnu'` 且模型是
`deepseek-flash` 时，把名字里的 `1017` 摘出来渲染成角标；其余模型原样返回 `model.name`。
同时复刻了官方那条判断——万一我们的注册把内置插件顶掉，官方模型的角标也照旧显示。
这个槽位给到的 props 是 `{ provider, model, t }`，返回字符串或 React 元素都可以。

**只有自部署那个标 1017**（上游就是 V4.1-Flash-1017 构建）。阿里云那个**不标**。

百炼文档（`help.aliyun.com/zh/model-studio/deepseek-api`）把这两个当成**两个独立的模型
ID** 分别介绍：

- `deepseek-v4.1-flash`：Responses API 只开华北2（北京）与新加坡；
- `deepseek-v4.1-flash-1017`：另外支持美国、德国、日本、中国香港共六个地域，
  并额外支持 `web_search` / `web_extractor` / `code_interpreter`。
  文档里没有任何"不带日期后缀就等同于某个快照"的说法。

而平台目录里这条模型的名字是 **`deepseek-v4.1-flash`（没有 `-1017` 后缀）**，
所以没有依据说它就是 1017 那个构建。

其它几条路也走不通：

- **平台不透出版本信息**：聊天 SSE 的 16 个字段里没有 `system_fingerprint`；
  目录只有 `model_name` / `model_id`(UUID) / `provider_name`，没有构建号。
  （自部署那条上游会返回 `system_fingerprint`，但那是 Open WebUI 网关的字段，
  跨平台没法直接比。）
- **模型自我报告不可信**：问自部署那个"你的版本"，它答「ChatGPT/GPT-4.1」。
- **行为比对只能证伪，不能证实**：6 道低区分度的题（1+1、反转、首都…）两个模型
  5 题逐字一致——这类题任何 LLM 都答一样；而且那次温度也没对齐（平台分支用的是
  插件内置温度）。不同量化/推理引擎/system prompt 都能表现一致。

结论：行为一致不算版本证据，百炼也把两者分列，所以在拿到明确依据前不标 1017。
### 同题异构对比（鹈鹕骑自行车，2026-10-31）

为了判断阿里云那个是不是更早的快照，让两个模型用**同一段提示词**各写一个
「内联 SVG + CSS/SMIL 动画」的 HTML 页面：鹈鹕骑车，要求车轮转、脚蹬、身体起伏，
只输出 HTML 不带解释。参数统一 temperature 0.7、思考开到最强。

| 模型 | 输出预算 | 结果 |
|---|---|---|
| 自部署 1017 | 8,192 | ❌ 0 字符，finish_reason=length（思考把预算烧光） |
| 自部署 1017 | 32,768 | ❌ 0 字符，同样被截断（思考 11 万字） |
| 自部署 1017 | 80,000 | ✅ 12,447 字符，12 个 SMIL 动画，画面有天空/太阳/花丛 |
| 阿里云 | 8,192 | ❌ 13,961 字符全是规划文本，没有 HTML |
| 阿里云 | 32,768 | ✅ 7,108 字符，6 个 SMIL 动画，画面较简，开头还留了一句说明 |

**结论：这个对比被输出预算强烈干扰，不能用来判断版本。**

- 预算给够时，自部署那个画得更丰富（天空、太阳、花草、帽子、翅膀，12 个动画）；
- 但**同等 32k 预算下，自部署那个直接失败（0 字符），阿里云反而产出了完整页面**——
  因为自部署模型的思考开销大得多。

所以"阿里云质量明显更差"这个前提不成立，**不标 0910**，继续保持不标版本号。
真要按质量定性，得先固定预算再测多轮多题，而且即便赢也证明不了权重相同。

## 请求体上限与多模态（2026-10-31 实测）

| 项目 | 实测结果 |
|---|---|
| 本地代理请求体 | 上限 **64 MB**（`maxBodyBytes`），超限返回 413 + `body_too_large`，不再是一句含糊的 `invalid json body` |
| 平台侧消息大小 | 1 MB 字符的消息实测正常返回（20s） |
| 自部署上游 | 200k / 320k 字的消息都能正常返回；网关限的是 **token**（prompt + max_tokens ≤ 300,000），不是字数 |
| 自部署多模态 | ✅ **真支持**。发 `content: [{type:'text'},{type:'image_url',image_url:{url:'data:image/png;base64,…'}}]`，模型能准确读出图里的文字（实测认出 `DSH-42-RED`） |
| 平台多模态 | ❌ 聊天接口**不传图**。文件能上传（`POST /chat/api/oss/file?application_id=…`，multipart 字段 `file`，返回 `./oss/file/<uuid>`），但聊天体里的 `image_list` / `document_list` 都被忽略，模型会回"未收到图片" |
| 网页端对照（2026-10-31 登录实测） | 「模型对话」页（`/portal/model-chat/:id`，kimi/qwen/deepseek 走的就是这条链路）**只有一个模型下拉 + 发送按钮，页面上 `input[type=file]` 数量为 0**，连附件入口都没有；「小海狮」等智能体页有「上传附件」，但 `accept` 只有 `.pdf,.docx,.doc,.txt,.md,.html,.csv,.xls,.xlsx`，**不含任何图片类型** |

因此模型目录里只有 `deepseek-flash` 声明 `input: ['text','image']`，三个平台模型是 `['text']`。

## 两条上游

同一个 provider（`hainnu`）下面挂四个模型，按请求里的 `model` 字段分流：

| 模型 | 来源 | 上游 |
|---|---|---|
| `deepseek-flash` | 海师自部署 | `chat.hainnu.edu.cn`（Open WebUI，OpenAI 兼容） |
| `kimi-k3` / `qwen3.8-flash` / `deepseek-v4.1-flash` | 海师阿里云 | 「海师大智汇」智能体平台（MaxKB 风格工作流 SSE） |

- **登录**：同一个学号密码，两条 OAuth2 链路（`/sso/oauth/login` 与
  `/portal/api/public/login/oauth2`）。两条链路的令牌分别存在 state 里，
  各自按 401 触发重登；重登共用同一份失败预算，不会把账号刷锁。
- **对话**：智能体平台的模型靠 `selected_model` 选，四个模型共用一个
  `is_router` 应用。多轮优先**复用平台会话**（只发新那条 user 消息），
  历史对不上（会话被清、消息被编辑）时新开会话并把整段上下文压成一条消息。
- **协议差异**：平台是 `text/event-stream`，帧里 `content` /
  `reasoning_content` 与 OpenAI 的 `delta` 对应，但**不能**带
  `Accept: text/event-stream`（网关会 500）。用量只在最后
  `is_end: true` 的那帧里，插件按 `chat_id` 归集后计入用量面板。

## 平台三个模型的参数（2026-10-31 实测）

参数来自平台的 `/portal/api/public/<portal>/model` 目录，行为用真实请求验证过：

| 模型 | 上下文 | 平台默认 `max_tokens` | 温度 | 思考 |
|---|---|---|---|---|
| `kimi-k3` | 1M | 8192 | 固定 1，**不可改**（改温度平台回 `Exception:Error code`） | 默认开，可关 |
| `qwen3.8-flash` | 256K | 2048 | 默认 0.7，可改 | 默认开，可关 |
| `deepseek-v4.1-flash` | 1M | 2048 | 默认 0.7，可改 | 默认开，可关 |

插件给 K3 / 阿里云 DeepSeek 申请 `max_tokens: 131072`、Qwen 申请 65536
（平台会真的兑现：实测 K3 一次吐出 108,893 字符、20000 行；给 200 则确实只有几百字，
说明这个上限是真实生效的）。早期统一给 8192，长任务因此容易「想到被截断」。

**思考档位**：平台没有「低/中/高」这种档位，只有一个开关 `enable_thinking`。
实测 `enable_thinking: false` 时三个模型的思考长度都归零；`thinking: {type:'disabled'}`
和 `reasoning_effort` 平台**不认**（会被忽略）。所以插件的映射是：
> 社区里有个直连百炼的插件说「kimi-k3 不允许关思考、发 `thinking:{type:'disabled'}` 会回一条
> 误导性的 400」——那是 **DashScope 直连**的方言，不适用于学校门户这条路。2026-10-31 在门户
> 这条链路复测过：`enable_thinking:false` → 思考 **0 字**、1.1 秒；`:true` → 736 字、6.0 秒。
> 社区项目的说法只作参考，以本仓库的实测为准。

- DSH 选 **off** → 请求里带 `enable_thinking: false`；
- 其它档位 → 不干预，用平台默认（开）。

写进 `cordis.patch.yml` 的 `reasoningEfforts` 是 `off: none` / `max: max`，
老配置里已有的 `low` 也照样能用（一律按「开」处理）。

**工具调用**：平台没有原生 function calling，插件用文本协议补上。0.2.0 起**两种格式都认**：

| 格式 | 例子 | 谁在用 |
|---|---|---|
| 插件协议 | `<tool_call>{"name":"run_code","arguments":{…}}</tool_call>` | 模型按插件提示输出 |
| DSH 原生 DSML | `<\|DSML\| invoke name="run_code">…<\|DSML\| parameter name="code" string="true">…` | 模型照着 DSH 系统提示输出 |

两种都会被解析成 OpenAI 的 `tool_calls` 增量（`finish_reason: "tool_calls"`）。
流式处理上，正文一旦出现任一标记就停止外发、转入捕获，避免把调用标记当正文吐给 DSH；
标记跨分片、漏闭标记、重复开标记这些情况都做了容错。

提示词里不再硬性要求某一种格式，而是写「按系统提示里给的格式输出，本代理两种都认」——
之前 K3 因为系统提示说 DSML、插件提示说 `<tool_call>` 而直接拒答，就是这里修掉的。

工具结果回来时，插件把结果接回**同一条平台会话**（`工具结果：…`），模型继续作答。
kimi-k3 / qwen3.8-flash / deepseek-v4.1-flash 三个都在 DSH 里实测跑通（能落盘写文件）。

### 提前收尾的自救（参考 kimi-for-dsh）

K3 在温度 1 下偶尔会输出一句计划（「我先看一下仓库结构」/「Let me read the file」）
然后**自然结束**，一个工具都不调。DSH 只会看到一次正常的工具回复，用户看到的就是
「它自己停了」。

插件在代理层做两层判定（思路参考过社区项目 kimi-for-dsh——该项目 2026-08 后已停更，
规则按我们自己的实测重写，不直接采信它的说法）：

1. **计划句**：开头是「我先 / 让我 / 接下来 / 先 / 现在先 / Let me / I'll…」，且整段
   不超过 240 字。「好的 / 嗯 / Sure / Okay」这类附和**不算**——必须后面还跟了明确的动手
   意图。另外三条排除规则：交付语气（总结 / 结论 / 短答 / let me know）、带冒号的
   结构化交付（「我先说明一下：…」）、以及尾句是「需要的话告诉我」这种交还用户的收尾。
2. **未竟意图尾巴**：只取最后一句，命中 `let me / 让我 / 接下来 / 先去…`，又不是
   「以上就是 / 完成 / done / 需要的话」这类完结语气，同时最近 8 条消息里有工具活动
   （说明是在干活中途断的，而不是闲聊收尾）。

命中后：**一律在同一条平台会话里追加**一条双语续接指令（`[auto-continue] …`）+
末尾的动作指令，不重开会话、不重发历史（10 轮对话实测：重发要 4739 字符，追加只要 287）。
首轮的会话还没记进续接表，用显式 `continueFrom` 带过去。只有「空回复重试」才换新会话重发。
最多 3 轮（无工具时 2 轮）。2026-10-31 用真实平台验证过：同会话追加续接指令后模型能正常
继续（nodeStatus SUCCESS），平台不排斥这种「没有工具结果、只有一句指令」的追加。

**规则是量出来的，不是照抄的**（21 条带标签样本，见 `test/portal-smoke.mjs`）：

| 规则 | precision | recall | 说明 |
|---|---|---|---|
| 社区规则（尾句意图 + 工具活动） | 0.67 | 0.60 | 漏掉「新会话首轮只说不做」；尾句法也漏「先检查一下依赖」 |
| 我们的规则（计划句 + 尾句，带三条排除） | **1.00** | **1.00** | 强/弱开头分开判，交付语气不触发 |

社区项目的「10 分钟 3 次」节流也模拟过：p=0.08（他们观察到的 2/24 早收尾率）时
无节流 1.1 次调用/百请求、有节流 1.0，收益可以忽略；而节流一旦生效，那一波里剩下的
早收尾就只能放任。所以**不采纳节流**，靠每请求最多 3 轮兜底。

2026-10-31 用真实平台跑了 4 个用例（3 个需要工具 + 1 个纯问答）：3/3 工具用例都是
**第一轮就发出 tool_calls**（`read`、`bash`、隐式「先看看 package.json」各一次），
耗时 4.7 / 15.4 / 5.6 秒，没有触发自救；纯问答 13.7 秒、221 字。自救只是兜底，正常路径
不多花轮次。


## 上游报错的语义映射

DSH 只按固定英文措辞给报错分类：看到 `context length exceeded` 才当上下文爆了
（触发自动压缩），看到 `insufficient quota` 才当配额用尽（终止重试）；其余一律算
普通 `INVALID_REQUEST` —— 上下文爆了不会压缩，配额用尽也会一直重试。

学校门户会把百炼的报错包成自己的格式（HTTP 400/429 + `{"code":…,"message":…}`），
原来的代码只回一句「海师大智汇对话返回 400」，语义全丢。现在：

| 上游文本 | 类别 | 回给 DSH | DSH 的处置 |
|---|---|---|---|
| `Range of input length should be [1, 1000000]`、`Your request exceeded model token limit` | `context_overflow` | **400** + `context length exceeded（…原文…）`，`code: context_window_exceeded` | 自动压缩后重试 |
| `You've reached your usage limit`、余额不足/欠费 | `quota` | **429** + `insufficient quota（…）`，`code: insufficient_quota` | 干净终止，不再白重试 |
| `rate limit` / 请求过于频繁 | `rate_limit` | **429** + `code: rate_limit_exceeded` | 退避重试 |
| 引擎过载 / 系统繁忙 | `overloaded` | 502（保持原状） | 退避重试 |
| 其它 | `upstream` | 502 | 按原逻辑 |

两个配套改动：

- **SSE 头延迟发**：以前一进 `handlePortalChat` 就写 200 头，上游随后报错也没法改状态码，
  只能静默 `end()` —— DSH 会当成正常结束。现在头延迟到第一帧真的有输出时才发
  （仍然是流式，只是不再抢跑），首包之前报错还能回 400 / 401 / 429。
- **流内错误帧**：已经推过帧之后才失败时，发一帧 OpenAI 风格的 `data: {"error":{…}}`
  再结束，客户端会当 `APIError` 抛出来，语义不至于丢。

## 模型策略（这条路由为什么特殊）

学校网关（Open WebUI）限制的是**单次请求体的字节数，约 1 MB**，不是模型上下文。
实测（同一个 400k 字符的提示）：

| 内容 | 字符 | 字节 | 结果 |
|---|---|---|---|
| 英文 | 400,000 | 400 KB | 200 |
| 中文 | 300,000 | 0.9 MB | 200 |
| 中文 | 340,000 | 1.02 MB | 200 |
| 中文 | 400,000 | 1.2 MB | **413** |

所以这条模型不能照抄官方规格。插件把 `contextWindow` 写成 300,000 是**给 DSH 的预算**，
不是声称模型上下文只有 300k（模型本身是 1M）；面板上它显示为「请求体上限 1 MB」。
写进 `cordis.patch.yml` 的参数：

| 位置 | 键 | 值 | 为什么 |
|---|---|---|---|
| 模型 | `contextWindow` | `300000` | DSH 的上下文预算；不是模型上下文，也不是网关原文（网关限的是约 1 MB 字节） |
| 模型 | `maxTokens` | `80000` | 网关默认只有 32,768；取 80,000 是为了让压缩线到 220,000（模型官方输出 64k） |
| 模型 | `input` | `text, image` | 模型支持图片输入 |
| 模型 | `reasoningEfforts` | `off: none` / `low: low` / `max: max` | 官方只有这三档 |
| provider | `compat.thinkingFormat` | `deepseek` | 决定思考字段怎么发 |
| provider | `compat.maxTokensField` | `max_tokens` | 网关只认 `max_tokens` |
| provider | `compat.supportsDeveloperRole` | `false` | 网关没有 developer 角色（插件代理也会把它转成 system） |
| provider | `reasoning` | `max` | 默认思考强度 |
| 压缩 | `compaction-basic.modelPolicies` | `headroomTokens: 0`、`maxTokens: 4000` | 见下 |
| 默认模型 | `agent-default-model` | `hainnu/deepseek-flash`、`reasoningEffort: max` | 新会话直接用海师 |

压缩线为什么必须单独调：DSH 的触发阈值是
`floor(min(W × 0.8, W − O − headroomTokens))`，`headroomTokens` 默认 65,536。

- 默认值下：`min(240,000, 300,000 − 80,000 − 65,536)` = **154,464**，一半上下文白扔。
- 插件写入的按模型覆盖：`min(240,000, 300,000 − 80,000 − 0)` = **220,000**，
  此时 prompt 220,000 + 输出上限 80,000 = 300,000，正好贴住 300,000 这条预算线
  （中文约 0.9 MB，仍在网关 1 MB 以内）。

写入范围刻意收紧：只写**按模型**的 `modelPolicies`（`provider: hainnu` + `model: deepseek-flash`），
不改 preset 里全局的 `headroomTokens`（那会连带影响其它 provider）；已经够高、或已有本模型覆盖时一律不动。

## 端口与接管

如果旧项目的 Python 代理还在跑并占着 8787，插件**不会抢端口**：它会探测 `127.0.0.1:8787/health`，
认出是同一个海师代理后直接「接管」（面板显示"接管外部实例"），模型配置一个字节都不改。
外部实例退出后，插件会在 30 秒内自己接管该端口。
如果 8787 被别的程序占着，插件会顺延到 8788 起，并把 `baseURL` 改成实际端口。

转发语义与旧项目 hainnu-proxy 保持一致：`role=developer → system`、`max_completion_tokens → max_tokens`、
SSE 原样透传、`429` 冷却 12 秒重试、`401` 触发一次重新登录、4 次退避重试、300 秒超时、
**直连上游不读 HTTP(S)_PROXY**（走本机代理常触发 Open WebUI 的 402）。

热重载不会重启进程。插件会把上一个实例的 server 主动收掉（`globalThis` 单例）；
从更早的手工调试版本升级上来的，重启一次 DSH 清掉遗留监听即可。

## 安全设计

- 密码与 JWT **只以密文落盘**：有 Electron `safeStorage`（Windows 上是 DPAPI）就用它，
  否则退回 AES-256-GCM + 本机派生密钥。明文既不写日志，也不经 HTTP 回传，
  面板只显示 `hasPassword` / `hasToken` 这类布尔量。
- 学校**连续 5 次密码错误会锁账号**，所以插件：自动登录失败 2 次后暂停自动重试（10 分钟窗口），
  手动登录不做任何盲目重试。
- 登录页目前没有验证码；万一门户改版出现验证码，插件会明确报 `captcha` 而不是硬撞。
- **两个端口都只监听回环地址，但"只监听回环"挡不住浏览器**（DNS 重绑定能让任意网页变成同源）。
  所以插件路由和 8787 代理都会校验 `Host` / `Origin` / `Sec-Fetch-Site`：来源说不清就 403，
  伪造 `Host: evil.example.com`、跨站 `Origin`、`Origin: null` 都会被拒。
- 密码**只准提交到学校自己的域名**：登录页里的 `<form action>` 必须落在
  `auth.hainnu.edu.cn:9443` 或 `chat.hainnu.edu.cn` 的 https origin 上，否则直接报错、
  一个字节的密码都不发出去（防门户被投毒/跳转被劫持把密码带去别处）。
- Cookie 罐**按域隔离**：没带 `Domain` 的按 host-only 存，带了只接受"当前主机或它的父域"；
  发给某一跳的 Cookie 必须和该 URL 的主机匹配。早期版本会把整罐 Cookie 发给任意跳转目标，
  一次跨站重定向就能把学校会话 Cookie 带出去。令牌也只认门户主机种下的那一个。
- 代理的本地 Key 校验**失败关闭**：一个 Key 都没配好时返回 401（而不是旧行为：直接放行）。
- 登录有进程级限流：10 分钟内失败 3 次就整体冷却 10 分钟，手动和自动登录共用同一份预算，
  避免被人反复触发 `/login` 把学校账号刷到锁定。
- 插件接口需要 DSH 自身的登录态（同源页面），不做单独鉴权；本机其它进程属于同一信任域，
  它们本来就能直接读 `~/.dsh/hainnu/state.json`。
- 走 DSH 远程访问（非回环地址）时，需要把 `allowRemote` 设为 `true`，否则面板请求会被 403。

## 已知限制

- 只实现 OpenAI 兼容（`/v1/chat/completions`）。旧项目的 Anthropic `/v1/messages`
  兼容层没有移植——DSH 用不到。
- 首次登录需要用户手动填一次密码；之后靠密文自动续期。
- 用量统计只覆盖「经过本插件代理」的请求；接管外部 Python 代理实例期间，那部分流量记不到。
- 「只说不做」的自救是**尾句启发式**：模型真的收尾了但最后一句像意图时可能多跑一轮；
  真的漏救时也只影响体验，不会破坏会话（下一轮还能继续）。
- 上游报错分类同样基于文本：百炼换措辞时正则要跟着更新。
